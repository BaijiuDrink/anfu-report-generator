# 模板驱动报告工作台后续开发工程计划

## 目标与边界

以合并后的 `main` 为唯一开发基线，把现有 PySide6 漏洞录入与固定版式 DOCX 生成工具，逐步扩展为本地优先、可使用不同 Word 模板的报告工作台。先让人工配置的模板稳定生成报告，再让 AI 辅助首次识别模板；没有 AI 时，录入和报告生成必须完整可用。

本文是跨阶段路线图，不是一次性实施指令。每个阶段启动前，应根据真实模板和前一阶段结果写独立的、可测试的实施计划。不得以本路线图为由大规模重写现有程序。

首发平台以 Windows 10/11 x64 为准。现有 Linux 基础功能不得回退；新模板能力在 Linux 通过独立验收前，不标称已支持。

## 当前基线

- `ProjectState` 和 `ProjectStore` 使用 `project_name + findings` JSON；截图以 `[截图: path]` 标记并在保存时复制到附件目录。
- `ReportService` 调用固定版式的 `ReportBuilder`，尚无模板 Schema、Word Mapping 或动态表单。
- 已有漏洞库、图文粘贴、POC/EXP、项目管理及 PySide6 工作台；这些功能必须保留。
- 合并前，`codex/poc-exp-code-block` 上的 UI、POC/EXP 和项目管理接线仍有未提交改动，主目录 `main` 也有未跟踪资料。先核对并只合并已验证的产品代码；不覆盖未跟踪资料，不自动推送远端。

## 路线与优先级

| 阶段 | 优先级 / 粗估 | 交付物 | 放行条件 |
| --- | --- | --- | --- |
| 0. 稳定基线 | P0 / 2-4 人日 | 合并后的 `main`、架构现状清单、旧 JSON 与当前报告回归样本、至少 3 份脱敏真实 DOCX | 完整测试、Windows EXE 启动、旧项目打开及固定报告生成通过；保留回退点 |
| 1. 统一数据与可靠保存 | P0 / 7-12 人日 | 版本化 Report Schema v1、Project/Report 分离、旧 JSON 导入导出、受管理证据、迁移与备份 | 旧项目无数据丢失；模板切换不删字段；项目移动后图片可用；中断写入可恢复 |
| 2. Word 后端可行性关口 | P1 / 3-5 人日 | 真实模板测试矩阵、Word Adapter 原型、具体后端和版本及分发许可决定 | 能定位目标字段、复制完整漏洞块、插入原图且不明显破坏页眉页脚与表格；失败则更换后端或缩小支持范围 |
| 3. 人工模板 MVP | P1 / 8-12 人日 | Template Schema v1、Mapping、模板库、编译器、确定性 Renderer、预检与预览 | 两份不同模板仅靠配置完成项目字段、漏洞重复块和证据图填充；原始 DOCX 不被覆盖；固定 Renderer 可回退 |
| 4. 模板驱动 GUI | P1 / 5-8 人日 | Schema 驱动的 PySide6 字段/模块、映射确认界面、后台任务 | 两模板显示不同表单；切换不丢数据；导入/预览/生成可取消且不会卡住 UI |
| 5. AI 模板识别 | P2 / 6-10 人日 | 可选 Provider、结构化候选 Mapping、人工审查、隐私设置 | AI 输出经解析和校验才能入库；用户可逐项改正；未配置 AI 仍可完成阶段 3-4 的流程 |
| 6. 内容助手及扩展 | P3 / 待真实反馈 | 措辞、摘要、复测辅助；新模板类型及 Linux 模板支持 | 不自动覆盖人工内容；逐项独立验收，不阻塞前面的可用版本 |

粗估按单人研发、已提供真实模板计算，不含客户侧脱敏和逐页人工验收。Word 格式保真是主要不确定项；阶段 2 的结果优先于时间估计。

## 各阶段实施包

### 0. 稳定基线

1. 核对 `main` 与开发工作树的提交、未提交文件和未跟踪资料；将已完成的功能改动单独提交，快进合并到 `main`，不自动清理其他工作树。
2. 在合并后的 `main` 上运行完整测试、格式和静态检查、Windows 打包与启动检查；以一个旧 JSON 执行打开、编辑、保存、生成报告的手工冒烟。
3. 收集简单模板、复杂重复漏洞表格模板、含多图模板各一份脱敏 DOCX；固定输入数据、期望 DOCX 和渲染页图。缺少真实样本时不开始模板编译器。

### 1. 数据模型与存储

1. 定义带 `schema_version` 的 `Project`、`Report`、`Scope`、`Asset`、`Finding`、`Evidence`、`Retest`。一个项目可有多份初测、复测或摘要报告；模板只控制显示、校验和排序，不拥有事实数据。
2. 为现有 JSON 提供显式迁移与导入/导出。长期存储可迁到 SQLite，但只能有一个事实数据源；迁移前备份，失败时原 JSON 保持可读。不得悄悄修改原项目。
3. 证据以受管理文件和内容哈希引用，保留原图；保存、备份及报告输出使用临时文件加原子替换。加入自动保存草稿和崩溃恢复，但恢复前需让用户选择。
4. 测试旧字段、空项目、多图片、移动项目、损坏附件、迁移中断及未知较新版本；较新版本不得被旧程序覆盖写回。

### 2-3. Word 模板能力

1. 先选定具体的 OfficeCLI 仓库/版本并检查许可证和离线行为；业务层只依赖 `WordAdapter` 的内部文档节点与操作，不直接依赖 CLI 原始 JSON。用 `subprocess` 参数列表调用，限制超时、输出和临时目录，不用 `shell=True`。
2. `Template Schema` 仅引用 Report Schema 的字段路径，独立版本化。Mapping 优先采用内容控件/SDT、书签、明确表格位置；文本锚点仅作为人工确认的回退。保留 `source.docx`、`compiled.docx` 和 `schema.json`，禁止覆盖源模板。
3. 首版必须支持“一条漏洞对应整块表格/段落”的重复区域、块内证据图片、条件显示、风险统计与日期/等级格式转换。宏、OLE、复杂 SmartArt 不做自动编辑；发现时提示限制或保留原样。
4. 渲染先预检缺失字段和图片，再在临时目录生成 DOCX，验证后原子替换目标。保留 `LegacyRenderer`。对真实样本逐页比较标题、页眉页脚、表格、分页与图片质量；不以“文件能打开”代替视觉验收。

### 4-5. GUI 与 AI

1. 用 Template Schema 生成现有 PySide6 表单中的模块与字段，不按模板新写页面；原项目数据保留未显示字段。长任务放后台，提供进度、取消、超时和清晰错误。
2. AI 只接收本地提取且经脱敏确认的必要结构、文本或页面；默认不上传真实报告内容。模型返回只能成为待审核候选 Schema，经过严格解析、版本/字段白名单验证和人工确认后才能编译。
3. 导入的 DOCX、JSON 和图片均是不可信输入：限制尺寸和压缩包展开量，不执行文档中的命令、表达式或 Prompt Injection；动态条件表达式不用 `eval`。API Key 不写进 EXE 或项目文件。

## 发布与停止规则

- 每阶段保留可运行的桌面版本、测试、变更记录和演示样本；失败不进入下一阶段。CI 同时运行旧项目兼容测试、固定报告回归测试和新模板视觉检查。
- Windows EXE 与模板处理工具分开验证。新增第三方二进制前记录来源、版本、哈希和许可证；Linux 包在同平台构建及测试。
- 不承诺任意 Word 模板 100% 自动识别。真实模板不符合首版边界时，给出可人工修正的 Mapping，而不是静默生成错误报告。
